# Business Context

## 1. What Problem Does This System Solve?

In financial lending operations, loan data is generated by two types of sources:

- **Internal systems** — the company's own loan origination platforms
- **External partner platforms** — third-party platforms that send loan disbursement data to the company for co-lending or servicing

In both cases, data quality problems are common:

- Missing required fields (no transaction date, no customer ID)
- Duplicate transaction IDs submitted across batches
- Invalid interest rates or loan amounts
- ID format violations that break downstream system integration

**The core business risk:** If bad data enters core systems unchecked, it creates downstream failures in financial reporting, risk models, regulatory filings, and repayment schedules. Fixing errors after ingestion is 5–10x more expensive than catching them at entry.

This system solves that by acting as a **validation gate** — blocking bad records before they enter core processing, and generating structured error logs for upstream correction.

## 2. Who Uses This System?

| Stakeholder | How They Use It |
|---|---|
| **Data Engineering Team** | Runs the validation pipeline on each incoming batch |
| **Finance / Accounting Team** | Reviews rejected records; monitors accounting consistency |
| **Risk Management Team** | Monitors rejection rates and error trends for credit risk signals |
| **External Partners** | Receives error logs to correct and resubmit failed records |
| **Compliance / Audit Team** | Uses validation logs as evidence of data governance controls |

## 3. Business Rules That Drive Validation

### 3.1 Why Disbursement ID Format Matters

Every disbursement must follow the format `DISBYYYYMMDDNNNNNN` (e.g., `DISB20260115000001`).

This format encodes the disbursement date and a sequence number, which:
- Enables date-based partitioning in data warehouses
- Supports idempotency checks (prevents double-disbursement)
- Ensures traceability back to source batch

### 3.2 Why Duplicate Detection Has Two Layers

**Batch-level duplicates** — the same disbursement ID appears twice in one incoming file. This often indicates a file generation or export error on the partner's side.

**Historical duplicates** — a disbursement ID in the incoming file already exists in the accepted core data. This is a critical idempotency violation that could cause double-counting in financial statements or risk models.

Both must be caught and rejected independently.

### 3.3 Why Interest Rate Is Capped at 36%

Many U.S. states have usury laws capping consumer loan interest rates. 36% APR is widely used as a regulatory threshold in consumer lending (aligned with the Military Lending Act and many state laws). Records exceeding this threshold are flagged as potentially non-compliant and rejected for review before processing.

### 3.4 Why Accounting Balance Must Be Exact

The system generates double-entry accounting records for every financial transaction. For every debit, there must be an equal credit. An imbalance — even of $0.01 — indicates a processing error that would corrupt the general ledger and produce incorrect financial statements.

### 3.5 Soft Warnings vs. Hard Rejections

| Type | Example | Action |
|---|---|---|
| **Strong (Hard Reject)** | Missing loan ID, duplicate disbursement, invalid amount | Record is **blocked** from entering core systems |
| **Soft (Warning)** | Missing region field | Record is **accepted but flagged** for downstream monitoring |

The distinction matters because over-rejection increases partner friction and processing delays, while under-rejection allows bad data into core systems.

## 4. Key Performance Indicators (KPIs)

The monthly monitoring report tracks:

| KPI | Target | Business Meaning |
|---|---|---|
| **Data Quality Score** | ≥ 95 | Composite score: 100 − (rejection rate × 70) − (soft warning rate × 10) |
| **Rejection Rate** | < 5% | Share of incoming records blocked by strong validation |
| **Soft Warning Rate** | < 10% | Share of records with incomplete optional fields |
| **Accounting Balance Pass Rate** | 100% | All accounting entries must balance |
| **Schedule Principal Match Rate** | 100% | Repayment schedule totals must equal loan amounts |

---

## 5. Business Impact of Data Quality Failures

| Error Type | Downstream Impact |
|---|---|
| Missing transaction date | Incorrect accrual period; financial statement errors |
| Duplicate disbursement ID | Double-counting in portfolio balance; inflated risk exposure |
| Invalid interest rate | Incorrect repayment schedule; compliance violation |
| Invalid disbursement amount | Incorrect loan receivable balance; audit finding |
| Accounting imbalance | General ledger integrity failure; regulatory reporting risk |

---

## 6. Real-World Parallels

This system reflects patterns used at financial institutions including:

- **Consumer lenders** (personal loans, BNPL): Partner data onboarding pipelines
- **Banks**: Pre-reconciliation validation for wholesale loan purchases
- **Fintech platforms**: API-based real-time validation before loan booking

The two-layer validation approach (hard reject + soft warning) is standard in production lending data pipelines at companies like Affirm, LendingClub, and SoFi.
